# Architecture

This guide covers the architectural patterns underlying the codebase. Read this when working on store/persistence/tick logic, or when an architectural question comes up that the spec doesn't answer.

For the *why* behind each pattern, see `PORT_PLAN.md` §5.

## State management — one Zustand store with slices

The entire game state lives in one Zustand store, composed of slices. Each slice owns one logical concern (currency, tree, canvas, workshop, ascend, skill tree, hover info, meta).

**Pattern:**

```ts
// src/store/<feature>Slice.ts
import type { StateCreator } from "zustand";

export interface FooSlice {
  fooValue: number;
  bumpFoo: () => void;
}

export const createFooSlice: StateCreator<FooSlice, [], [], FooSlice> = (set) => ({
  fooValue: 0,
  bumpFoo: () => set((s) => ({ fooValue: s.fooValue + 1 })),
});
```

**Combined in `src/store/index.ts`:**

```ts
export type GameStore = MetaSlice & CurrencySlice & TreeSlice & /* ... */;

export const useGameStore = create<GameStore>()(
  persist(
    (...a) => ({
      ...createMetaSlice(...a),
      ...createCurrencySlice(...a),
      // ...
    }),
    { /* persist config */ },
  ),
);
```

**Why one store, not many:** cross-slice reads are natural (slice A's action can call `get()` and read slice B). Many independent stores would force explicit subscription chains and lose the cohesion that makes the game easy to reason about.

**Component subscriptions:** always use selectors.

```ts
// good
const gold = useGameStore((s) => s.gold);

// bad — re-renders on every state change
const state = useGameStore();
```

## Persistence — IndexedDB via SaveAdapter

`src/systems/persistence.ts` defines a `SaveAdapter` interface. The Day-1 implementation is `idbAdapter` backed by `idb-keyval`.

```ts
export type SaveAdapter = StateStorage;

export const idbAdapter: SaveAdapter = {
  getItem: async (name) => (await get<string>(name)) ?? null,
  setItem: async (name, value) => set(name, value),
  removeItem: async (name) => del(name),
};
```

**Usage:**

```ts
persist(creator, {
  name: "artdle-save",
  version: 1,
  storage: createJSONStorage(() => idbAdapter, serializer),
  migrate,
  partialize: (s) => { /* exclude transient state */ },
})
```

**Big-number serialization.** `break_eternity.js` `Decimal` instances don't round-trip through plain JSON. Use the custom `replacer`/`reviver` in `src/store/index.ts` that wraps `Decimal` values as `{ __big: "..." }` shapes.

**Async rehydration.** IDB reads are async. The first render after app startup MUST gate on `useGameStore.persist.hasHydrated()` — see `src/main.tsx` Bootstrap. Without this gate, the UI flashes default values before snapping to persisted values.

**Future trajectory.** The same `SaveAdapter` interface is implemented by a future `RemoteSyncAdapter` (v3.x): read from IDB, push to server. The store doesn't know.

## Versioned migrations

Save schema is versioned (currently `version: 1`). The `migrate` callback in `persist` is the migration chain. v1 is a no-op (no prior version to migrate from), but the chain stub exists so future waves can append:

```ts
const migrate = (persisted: unknown, fromVersion: number): GameStore => {
  let state = persisted as GameStore;
  if (fromVersion < 2) state = migrateToV2(state);
  if (fromVersion < 3) state = migrateToV3(state);
  return state;
};
```

**Discipline:** every save schema change ships a migration. Skipping migrations breaks every existing save.

**Failure mode:** if migrate throws, present a "save corrupted — start new run" modal (v1 stub: a confirm dialog).

## playerId

`playerId` is a UUID v4 generated by the meta slice initializer. On a fresh save (no IDB data), the initializer's value stays. On a returning save, persist rehydration overwrites the in-memory value with the saved one. After the rehydration gate clears, `playerId` is set and stable.

**Preservation across ascends:** ascend resets gold/inspiration/canvas/tree. It does NOT touch `playerId`, `ascendCount`, `fame`, or `purchasedSkillNodes`. Always merge state on reset, never replace.

## Tick loop — RAF + visibilitychange

`src/core/tickLoop.ts` runs on `requestAnimationFrame`. Each frame computes a delta in seconds (capped at 1s to avoid stutter-induced fast-forward) and calls a registered tick function.

**Visibility:** when the tab hides, RAF stops. When it returns, the loop resumes from `now` — no offline catch-up in v1. The 24h F-style hybrid catch-up arrives in v2.0.

**Tick discipline:** the registered tick function should be deterministic — given the same delta, produces the same state change. No reads from `Date.now()` inside subsystem ticks; pass `delta` only.

## Big numbers — break_eternity.js

`src/core/bigNumber.ts` wraps `break_eternity.js` `Decimal` as the project's `Big` type.

**When to use Big:**
- Currencies (gold, inspiration, fame). Plain numbers overflow on long runs.
- Palier formulas (`1000 × 2^count` exceeds `Number.MAX_SAFE_INTEGER` around count=53).
- Any quantity that can compound exponentially with multipliers.

**When plain `number` is fine:**
- Counts, indexes, levels (always small integers).
- Time deltas (always seconds, < 1.0 in normal ticks).
- RNG outputs ([0, 1)).

**Helper exports:** `big(n)`, `ZERO`, `ONE`, `max(a, b)`, `min(a, b)`, `isBig(x)`.

## RNG — seedable for tests

`src/core/rng.ts` exports `setSeed`, `rng()` ([0, 1)), `rngInt(min, max)` (inclusive), `rngFloat`, `rngPick(arr)`.

**In production:** seeded once on app start with `Date.now()`. No re-seeding during play.

**In tests:** every RNG-touching test calls `setSeed(42)` (or another fixed seed) in `beforeEach` for determinism. Don't write tests that assume `rng()` matches a hardcoded value across versions of `break_eternity.js` — only assume *the same seed gives the same sequence within one test*.

## Hover info — fixed strip, not tooltip

The InfoPanel sits above the BottomBar, always visible. It reads three fields (`hoverTitle`, `hoverBody`, `hoverFooter`) from the `hoverInfoSlice`. Components push hover info via the `<Hoverable>` wrapper on `onMouseEnter`, clear on `onMouseLeave`.

**Don't reach for Radix Tooltip / Popover / similar overlay primitives.** That's the wrong pattern — the InfoPanel is structural, not floating.

**Content authoring rules** (from `docs/specs/2026-04-25-info-panel-design.md` §6):
1. Numbers always (magnitude + current value)
2. Costs always (in footer, with currency icon)
3. State always (current level, count, fraction)
4. Concept entries explain what the thing IS *and* what it gives you concretely
5. `title` = label, `body` = effect with numbers inline, `footer` = cost/state
6. Use `() =>` callbacks for live values
7. Numbers via `formatter.ts` short-form

## Formulas — `balance.ts` is the single source

Every gameplay formula lives in `src/core/balance.ts`. Every formula has a Vitest test in `tests/core/balance.test.ts`. Discipline copied from the Godot rebuild's MVP rescope spec §12.

**Why centralize:** balance pass becomes one file to retune. Tests pin behavior. Re-tuning doesn't require refactoring callers.

**Tuning constants** are exported as named constants (e.g., `PALIER_BASE`, `PALIER_GROWTH`, `FAME_LOG_K`). Don't inline magic numbers in formulas.

## File structure rationale

```
src/core/      — pure utilities, zero React, zero store. Importable by anything.
src/config/    — data only (no logic). Tree stages, affix pools, skill tree nodes.
src/store/     — Zustand slices + combined index.ts. Where state lives.
src/systems/   — logic awkward inside slices (orchestrated reset, persistence adapter).
src/ui/        — React components. Subscribe via selectors, dispatch via slice actions.
tests/         — mirrors src/ structure exactly.
```

**Test naming:** `<file>.test.ts` for unit tests. Integration tests use `<feature>-integration.test.ts` (e.g., `persistence-integration.test.ts`).
